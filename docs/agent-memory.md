# 会序 Agent 长期记忆设计

## 1. 团队希望记住什么

团队一年办多场活动。换场救援的经验、场地使用限制、审批流程和筹备模板如果只留在对话里，下次活动还得从原始材料重新找。与此同时，历史活动里的报价、嘉宾时间和场地容量可能早已变化。负责人需要知道 Agent 查到了什么、当时适用于哪场活动，以及这次还要确认什么。

会序采用 LLM Wiki 的整理方式。新资料进入后持续更新主题页、保留原文引用、维护索引与变更日志，查询时先复用已整理的知识。Karpathy 的原始说明提出原始资料、Wiki 与维护约定三个部分，以及入库、查询、巡检三种操作。下文的权限、发布版本、切片和审核规则是会序的产品设计。 [Karpathy 的 LLM Wiki 原文](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

当前本机实现已把导入、原件、切片、版本及关键词索引持久化到 SQLite。压缩包按成员提取，图片及扫描页可通过本机 OCR 建立索引。用户可检索并导出资料索引知识页。Agent 的检索工具按当前活动读取用户允许引用的片段。后续设计仍包括团队身份权限、跨活动知识审核及恢复流程。活动计划和执行状态当前仍在浏览器保存。

## 2. 业务事实、原文和知识页

| 内容 | 存什么 | 回答时如何使用 |
| --- | --- | --- |
| 业务记录 | 活动计划草稿、已发布版本、现场实绩、报名、实时可用场地和已确认报价 | 问当前安排时查当前发布版，问草稿时按草稿读取，问实际发生时间时查实绩。涉及执行时重新校验实时状态 |
| 原始资料 | 每版 PDF、Excel、文档、图片和按权限保留的业务记录或外部回复 | 用于核对原文，保留文档版本和页码、行号或图片位置。文件更新产生新版本，按保留策略处置旧版本 |
| Wiki 知识页 | 活动交接、复盘案例、筹备手册、场地设备经验和团队偏好 | 提供背景、历史做法和可复用步骤。每条事实能回到证据，历史与适用范围随页面展示 |
| 维护约定 | 页面模板、分级、审核角色、索引、巡检规则和变更日志 | 约束知识的写入与引用。索引是内容目录，日志是维护历史，两者都继承访问权限 |

组织是权限边界。知识页可以仅对单场活动成员开放，也可以是团队共享手册。个人偏好须由本人明确保存，默认只在本人权限内生效。跨活动复用仅带入已审核的团队规则、模板和脱敏案例。联系人、签到凭证、私有课件和未公开报价留在受控业务记录或原始资料中。生成共享案例时移除姓名、联系信息和可访问受限资料的链接；原文引用仍按请求人权限解析。

## 3. 切片和引用

按能单独核对的业务含义切分。段落检索用 250–600 tokens 作为初始调试范围，超过约 800 tokens 再按子标题或条款拆分。完整表格行、关联条款和短决策记录优先保持原样。上下文不足时带上上级标题或表头，引用时定位实际使用的段落、行或区域。数值是实施起点，随真实样例的召回与引用定位效果调校。

| 来源 | 切片单元 | 定位字段 |
| --- | --- | --- |
| PDF、Word | 标题下的一段或一条规则。场地布置要求与适用条件相邻时放在同片 | 文件版本、页码、标题路径、段落或坐标 |
| Excel、CSV | 一个场次、一个场地或一个报价记录。跨行记录作为一组，保留表头、单位及区分报价版本的列 | 工作表、行号区间、单元格或范围 |
| 海报、截图 | 一块可独立理解的区域，例如议程时间、地点、二维码说明。记录识别不确定项 | 图片版本、区域坐标、识别状态 |
| 压缩包 | 按成员文件解析，再按对应文档规则切片 | 压缩包版本、成员路径、页码或行号 |
| 发布、现场、复盘 | 一次变更决定、一次事件或一条复盘结论。记录原因、选择、结果和适用条件 | 活动、记录 ID、业务版本、发生时间 |

每个切片记录 `organization_id`、`event_id`（团队共享时为空）、`source_id`、`source_revision`、`locator`、`content_hash`、`access_scope`。以 `source_id + source_revision + locator` 标识原文位置，用 `content_hash` 辅助去重；重复上传不重复产生知识提案。Wiki 页有独立 `page_id` 和 `revision`，正文按小节检索，并用证据列表把结论绑定到一个或多个原文位置。跨页时间表保留行所在页和继承表头，避免把两页里不同行的时间和场地拼在一起。

## 4. 何时沉淀说明文档

| 触发点 | 知识页 | 纳入内容与确认方式 |
| --- | --- | --- |
| 新资料导入并核对 | 活动资料摘要、场地档案 | 文件范围、有效日期、已确认值、仍待确认的冲突。文档识别结果先标为待核对 |
| 活动发布或现场交接 | 版本交接说明 | 发布版本、变更原因、受影响岗位、剩余任务和相关业务链接。变更事实随已确认记录更新 |
| 活动结束并复盘 | 事件复盘、筹备或救场手册 | 方案、结果、适用条件和后续改进。跨活动复用的规则由负责人确认 |
| 用户明确要求记住 | 个人偏好、团队约定或候选说明页 | 保存前明确范围，允许修订、撤回或删除。团队约定走团队审核 |

页面包含标题、适用组织和活动类型、负责人、状态、适用条件、正文、引用、最近核验时间和替代版本。状态使用「待核对、有效、存在冲突、已被替代、已归档」。同一主题有新来源时优先更新现有页。高影响事实出现不同值时把两条原文并列并等待负责人处理。对话可以提炼成候选说明，核对后才作为共享知识使用。

按组织和访问范围提供可导出的 Markdown 目录。目录由服务端记录生成，知识页引用受控原文的位置。

```text
schema.md                         维护约定与页面模板
index.md                          可访问知识页目录
log.md                            授权范围内的维护摘要
events/<event-id>/handover.md      活动交接和当前引用版本
events/<event-id>/retrospect.md    活动复盘和候选改进
playbooks/venue-closure.md         已审核的团队换厅手册
```

**示例知识页 · 会场关闭时如何换厅**

- **状态**　待审核的团队救场手册，来源为虚构 150 人论坛的变更单与复盘。
- **适用条件**　原会场关闭，分场已有确认报名，仍有其他可用场地。
- **历史案例**　当时 72 人已确认，B 厅容量 60 且缺无线麦克风。C 厅容量 90，清场后留 10 分钟布置，工作坊发布至 C 厅 14:20–15:00。
- **可复用步骤**　查当前确认人数、设备、清场时间、嘉宾与岗位可用性。比较候选后，从变更单同步议程、台本、签到点和相关通知。
- **证据**　关联当次 `change_id`、发布 `v2` 与复盘记录。新活动引用的是上述检查步骤；容量、时间和可用性重新读取本场业务记录。

## 5. 查询、更新和恢复

1. **确定范围。** 读取当前请求人的组织、活动、角色及问题所指版本。先按权限限定候选来源和页面，再做检索。跨活动搜索使用已授权的共享知识；历史活动详情仍单独授权。
2. **选取证据。** 当前执行问题直接读业务记录。复用经验先走知识目录、标题和关键词检索，再读取相关小节并核对原文。规模增大后，可按实际检索评测加入向量或混合召回。索引和缓存要接受同样的权限和撤回约束。
3. **回答或提议。** 说明来源、版本和适用时间。对未确认或互相冲突的信息展示并排证据。检索为空、知识过期或来源受限时，给出仍需确认的字段。调用排程、发布或发送前复查业务状态并走原有确认流程。
4. **持久化。** 原文使用带版本的受控文件存储；权限、业务记录、页面版本、引用关系和维护任务使用服务端持久化。入库与业务提交用可靠事件触发；以事件 ID 和目标修订去重。任务失败可重试，已发布知识继续可读；旧页面标明核验时间，当前执行始终从业务系统取值。
5. **校验与恢复。** 变更时更新相关页面和索引。定期检查断链、权限变化、未处理冲突、重复页和过期结论。撤销来源权限时立即阻止访问，并重算受影响摘要、检索索引及缓存。备份文件、记录和修订日志，验证重建索引及跨会话恢复。日志记录操作者、来源、变更和状态，避免写入敏感原文。

## 6. 交付顺序与验收

| 交付 | 可验证结果 |
| --- | --- |
| 原文版本、定位、权限和确认记录 | PDF 14:00 与海报 14:30 并列可查，更新原文后旧证据保留历史版本；权限撤销后搜索、引用与已生成摘要均按范围处理 |
| Wiki 页、维护流程和重试 | 同一份资料或事件重试只生成一次修订；同一结论更新原页并可查变更；失败后可恢复，索引可重建 |
| 检索和业务协作 | 新会话问当前工作坊，返回发布 v2 的 C 厅时间；问旧方案或实际开始时间，分别返回对应记录；索引落后时仍能读取当前业务事实 |
| 跨活动复用和恢复演练 | 下一场论坛找到已审核换厅手册，重新核验现场数据；其他团队检索不到该案例；删除或撤权后缓存与索引不泄露；恢复备份后仍能找回可访问的知识和证据 |
